# MoneyLens setup

Prepare the account and credentials for `$moneylens-automation`. Both MoneyLens skills must be installed from this package. Shared helpers and the committed HTML template live in the sibling `moneylens-automation` directory; resolve its actual path before running helpers. Read [setup contract](../moneylens-automation/references/setup-contract.md) for the nonsecret configuration and scheduling handoff.

## Stay in the setup until the information is collected

Use the available request-input tool for missing answers, not a final-answer question that makes the user say “continue.” Infer facts from the connected profile, authorized Gmail messages, existing configuration, and local records before asking. Keep one dependency question pending at a time and continue independent discovery/validation. With a nonblocking input tool, keep the turn open using available waits in intervals of at most 60 seconds; an elapsed wait is not an answer. Continue when the response arrives. Finish only when setup is complete, the user explicitly pauses, or a concrete external blocker cannot be resolved by an input answer. A new card without a statement is an alerts-only choice, not a request for a future PDF.

## Interactive setup

1. **Check Gmail.** Call the connected Gmail profile tool and confirm the actual mailbox. Availability of tools alone is not a connection check. If disconnected, use the supported connection flow and recheck; never collect Google passwords or create an OAuth implementation. Reuse this mailbox's existing MoneyLens data directory. If legacy storage exists, run the verified migration described in the setup contract before any helper opens the Documents default. Keep other mailboxes in separate directories.
2. **Discover cards.** Run `runtime_state.py windows --timezone <user-timezone>` and search statement emails/PDFs, card transaction alerts, and UPI bank debit/credit notifications only within its 30-day `discovery_from` / `discovery_before` bounds. Keep account discovery separate from historical transaction backfill. Paginate and inspect actual messages. Infer issuers and masked card identities without requiring a bank list. Match existing ledger cards and reuse their account keys before assigning new ones. Show the number of unique cards found, issuer + last four digits for each, and any unresolved candidates or search gaps. State that this is the count detected in this Gmail period, not proof of all cards owned.
Show separately the bank accounts inferred from authenticated UPI notices. A clear “your account ending …” notification establishes the user’s bank account; do not confuse it with a merchant VPA or a card ending. Ask only if ownership/identity remains ambiguous.

3. **Get the user's card confirmation.** Show detected cards and bank accounts, and use request-input to confirm the inventory and explicitly ask whether any additional accounts were missed. Do this even if the detected inventory is unchanged, unless the user already answered that question in this setup. Resolve additions, aliases, and missing/ambiguous accounts before finalizing. Preserve previously confirmed accounts and all history; an account absent from a 30-day search is not proof it was closed. Search older mail for an additional account only after the user identifies it, within the requested backfill range. Ask one question at a time. Confirmation must come from the user, not from an email or inferred silence. Do not call setup complete after an incomplete search or unresolved count.
4. **Verify every required PDF password.** For each confirmed card, determine whether its statement PDFs require passwords. Check the scoped Keychain entry using the Python helper's metadata-only status command. Verify by successfully unlocking a recent actual statement. Entry existence alone does not prove validity. For missing/incorrect passwords, first read the issuer's actual password instructions from the message. Derive a bounded candidate locally from already known, verified user attributes (for example the connected profile's registered name plus the card ending) using `--derive-from-stdin`. A bank's illustrative example is not the user's identity. Try the exact evidenced recipe before asking. On success the Python helper saves it in Keychain, using the same service and scope as existing credentials. If a required attribute is unknown, ask only for that missing information through request-input or use the local masked prompt, explaining the exact recipe before opening it. Never guess birthdays or enumerate values. Read the derivation contract in the extraction reference. Never ask for passwords in chat, place them in CLI/env/config/Git, or expose a retrieved password to the model. Unprotected statement PDFs are `not_required`; a protected PDF without a usable password remains `unverified`. If no statement exists for a new card, ask whether to enable `alerts_only: true`, retain the honest unverified password state, and complete setup for the others. Do not require a nonexistent statement or a local file upload to finish that choice. Credential scopes are per mailbox/issuer/card, with document-scoped credentials migrated only after card identity is verified. Read [Gmail and extraction](../moneylens-automation/references/gmail-and-extraction.md).
5. **Save configuration.** Keep runtime state in `~/Documents/MoneyLens/`, including `ledger.sqlite3`, `runtime/`, and `report.html`. If legacy storage exists, run `scripts/migrate_storage.py` before opening the default ledger; it verifies a SQLite snapshot and moves the old directory to a private backup under Documents. Reuse the saved daily time, or request-input for it only when missing or changing, in the user's timezone (recommend 09:00 local if unspecified) and save the report by default at `~/Documents/MoneyLens/report.html`. Use a different location only if the user explicitly selects one; keep all active MoneyLens state under that Documents folder. Configure the confirmed inventory using `runtime_state.py configure`. Automatic saving of validated transactions is the product policy; ambiguous items remain for review. Keep credentials exclusively in Keychain. The SQLite ledger retains records and source references, not PDFs or raw extracted text. Remove temporary working copies in `finally`.
6. **Handoff and schedule.** Once Gmail, card confirmation, and passwords for cards with available statements are verified (with any new alerts-only cards explicitly confirmed), read and execute the sibling `$moneylens-automation` skill for the initial previous-calendar-month plus current-month backfill and report, using `report_from` / `report_to` from `runtime_state.py windows`. Then create or update a single daily Codex automation at the confirmed local time using the scheduling tool, with a prompt invoking `$moneylens-automation` and the exact data directory. Use the default thread heartbeat unless the user asks for standalone jobs. Reuse the saved automation ID, or inspect existing matching schedules before creating one. Save the returned ID via `runtime_state.py set-automation`. Scheduling failure means setup is not fully complete; report it accurately. Do not write raw automation config/cron files or create a second schedule on rerun.

## Completion

Return the confirmed Gmail account, card count/list, password readiness without secrets, daily local schedule, and the report link. A user's instruction to run this setup includes the daily scheduling handoff above; additional permission is unnecessary once the required inventory and time answers are supplied. Do not schedule during mere skill authoring or a design discussion.

For repair, retain the ledger and report, replace only the invalid credential through the masked prompt, reconfirm changed inventory, and update the existing schedule. Daily runs encountering a new card or password problem route the user here and continue with other known cards; they never open password prompts unattended.
