# Set up MoneyLens

In command examples, `<pdf-extract>` means `<python> <automation-skill>/scripts/pdf_extract.py`, the separate PDF tool. `<moneylens>` means `<python> <automation-skill>/scripts/moneylens.py`, using the installed Python 3.10+ and the absolute directory of the automation skill (the sibling `automation` directory when reading setup). Quote paths for the current shell; keep each command argument as a separate argument.

Follow these five steps in order. Scheduling is the final step: do not ask about refresh frequency, suggest a time, show an automation proposal, or create a schedule during mailbox discovery, account confirmation, PDF unlocking, or the initial data import. Complete statement access and the first report before raising scheduling. When resuming, recheck email MCP access, then reuse confirmed choices and private source-inventory notes. Merely authoring or reviewing this skill does not authorize reading email, provisioning credentials, generating a personal report, or scheduling jobs.

When user input is needed, use the host's available structured input tool, such as `request_user_input`, `request_user_input_async`, or `ask_user`, in the current mode. Ask exactly one question per tool call and request only one value or decision in that question: the UI has one text-input field. Never combine two details, even related ones, into one prompt or submit a list of questions. For example, request a missing refresh time and a missing timezone separately; never request a name and birthdate together. Wait for the answer before asking the next question. Reuse answers and authorizations already provided, and continue independent checks while waiting. Ask scheduling questions only in step 5. If no suitable input tool is available, ask one concise question in chat and wait. Sensitive credential inputs must follow the private credential workflow below.

Prefer deterministic tools, static rules from explicit inputs, and saved mappings over LLM reasoning. Reuse confirmed account identities, cached categories, and verified credentials. Reserve model interpretation for new or ambiguous source content and uncached merchant decisions; do not repeat it for known cases. This does not authorize adding institution-specific assumptions or moving MCP retrieval into scripts.

## 1. Resolve email access through MCP

Discover the available email MCP tools and verify a live connection to the user's mailbox through the provider's supported account/profile operation. Tool presence alone is not proof of a connected account. Verify supported search, message reading, account routing, and attachment retrieval capabilities; never invent tool arguments or download endpoints.

**Stop setup if the user has no connected email MCP provider.** Point them to Plugins to install an email provider plugin and connect their account, or reconnect an installed provider whose access has expired. State what is missing and resume only after MCP access is verified. Do not work around this gate with browser access, custom OAuth, IMAP, local mail files, exports, uploads, or manually supplied statements.

List verified mailbox addresses. Reuse an explicit selection already authorized for this setup or its recurring refreshes. If that scope is missing or ambiguous and more than one mailbox is available, ask which account(s) to use and wait. Never infer all accounts merely from saved configuration or a prior run. Before accessing each selected mailbox's content, state “Pulling information from <email address>.” Keep unselected mailboxes' content and source inventory untouched.

Use the connected provider's documented search and retrieval operations. Shared references include provider-specific examples; verify that the connected provider supports the required operations and source evidence. If the connected provider cannot supply the required source evidence, explain the specific limitation and hold that source for review rather than creating another access route.

## 2. Search recent financial emails and statements

Resolve the sibling [automation skill](../automation/SKILL.md) and its helpers. Keep existing private data paths and read `<moneylens> accounts --data-dir <directory>` to reuse confirmed accounts, preferences, and progress. Resolve the installed Python 3.10+ command as `<python>` and use maintained helpers. Read the [setup contract](../automation/references/setup-contract.md) for state schemas; defer local extraction/report checks until needed in steps 3–4.

The agent computes rolling 30-day discovery bounds in the user's timezone and passes date filters directly to MCP. Search and paginate each selected mailbox for these sources separately, adapting terms to the user's language, observed institutions, and local payment systems:

- Credit-card purchase, debit, credit, refund, and repayment notices, plus card statements.
- Bank-account debits, credits, transfers, payments, receipts, and bank/account statements, including savings, current/checking, and consolidated statements.
- Instant payments, domestic/interbank transfers, direct debits, wires, and wallet/payment-service notices. Use systems actually evidenced by the selected sources, without a country-specific catalog.

Search statements independently from transaction alerts. Include attachments and actual statement tables in email bodies; do not require attachments for every search. Refine generic terms such as statement, transaction, paid, received, debited, credited, and transfer with observed sender/subject vocabulary. Do not limit discovery to known issuers or layouts supported by a parser.

Read the full enclosing messages, including HTML and inline/attached instruction images, not just search snippets or extracted text. A plain-text view or an attachment flag can omit image-only instructions; retrieve and inspect the relevant image through supported MCP operations before declaring instructions missing. Capture statement periods, masked account identity, attachment metadata, and any password/unlocking instructions for step 3. Use authorized attachment retrieval and, where supported, the parent message's raw MIME route; read [Email and extraction](../automation/references/email-and-extraction.md) for shared extraction guidance and provider-specific details. Do not automatically follow sign-in, payment, or external statement-download links. Unsupported formats or unavailable attachments remain visible issues.

Keep successful financial movements distinct from OTPs, promotions, declined attempts, reminders, balance-only notices, and authorization holds. A generic incoming credit is not automatically income or a refund. Preserve account, currency, amount, transaction date, reference, and source provenance when available. Disclose search/pagination failures and actual date coverage.

Show discovered cards and bank/payment accounts separately, including institution, source-provided masked identifier, and available product/network/holder distinctions. Confirm only unresolved account decisions, one per question. Ask about missing accounts separately instead of combining that request with inventory confirmation; reuse information already confirmed. Search older mail for user-identified missing accounts within the intended backfill period. Save the confirmed inventory and authorized recurring mailbox scope in the private source inventory.

Use stable opaque mailbox/account keys and preserve earlier confirmed identities. Institution plus ending is only a candidate match; colliding endings require distinguishing evidence. Never select the first ambiguous account or silently add a discovered account to the ledger. Use only `mailboxes`, `bank_accounts`, and `credential_scope` in the current settings schema.

## 3. Read statement password instructions, then resolve missing inputs

Retrieve and probe the selected statement PDFs. Read unprotected PDFs and try the exact verified saved credential for each protected document's confirmed scope. Resolve missing unlock details and actually decrypt/read the protected PDFs before moving to scheduling; announcing that these checks will happen next does not complete this step. Ask only the remaining source/access questions here.

For each protected statement, **read its enclosing email's actual unlocking instructions, including instructions inside images, before asking for missing identity inputs**. Retrieve relevant inline/attached image bytes through MCP or its supported raw-MIME route. Prefer available local OCR for readable text; use image inspection when needed and check the original pixels for case, digits, and punctuation. Then search the web for the actual issuer's official guidance for the same statement type and compare the documented format. Public guidance corroborates the instructions; only a successful local unlock verifies this PDF. Record source-image provenance and the public guidance URL/status without private values. If the image is inaccessible, guidance conflicts, or confirmation is unavailable, retain the precise gap rather than inventing a recipe or claiming confirmation. See [image instructions and web confirmation](../automation/references/email-and-extraction.md#instructions-contained-in-email-images). Do not assume an issuer's usual recipe or try unrelated saved credentials.

Determine exactly which identifiers and formatting the recipe requires: for example, name characters and case, phone suffix, date of birth format, or card/account suffix. Reuse verified details from authorized evidence and existing setup state. Ask only for required inputs that are still unknown or ambiguous after checking the email, its instruction images, official public guidance, and existing authorized evidence. Request one missing input at a time, using the least detail the recipe needs. Do not ask the user to repeat known details or supply a separate password when the documented recipe can derive it. Never guess identity details, enumerate birthdays, or use example identities from the email.

Do not conclude that a statement cannot be decrypted without additional secrets until the applicable unlock instructions have been exhaustively evaluated. This means inspecting all relevant email text/HTML and instruction images through available supported retrieval routes, checking applicable official issuer guidance, resolving the recipe's exact formatting, and comparing every required input with existing authorized evidence and the exact scoped saved credential. Evaluate all documented instructions; test only bounded, source-supported candidates. An encryption flag, missing saved password, failed candidate, inaccessible image, or incomplete search alone does not establish that new secrets are needed. If instructions remain unread or ambiguous, report that precise instruction/access gap and keep readiness `unverified`. Only identify an additional private input as required when a verified applicable instruction requires it and the input is demonstrably unavailable; explain that nonsecret dependency and request just that one input through the private workflow. Exhaustive instruction review never means guessing identity details or brute-forcing passwords.

Before local extraction, run the capability checks in the [setup contract](../automation/references/setup-contract.md): verify the helpers, PDF dependencies, and owner-only writable storage independently of email access. Use the host's actual capabilities and resolved paths. The agent applies the document's exact recipe to verified inputs, then passes one to three document-supported password candidates in a transient stdin object `{"passwords":["<candidate>"]}` through `<pdf-extract> --passwords-from-stdin`. The PDF script contains no password recipes, identity-format rules, or issuer catalog. Missing or ambiguous instructions remain unresolved; do not substitute guessed combinations.

Save only a derived result that unlocks the actual PDF, then repeat extraction with `--no-prompt` to prove reuse. The supported `private-file` store keeps verified derived passwords in the private data directory's `credentials/` folder, outside installed skills and Git. It is plaintext at rest, with owner-only POSIX permissions or protected current-user Windows ACLs. Normal setup authorizes this storage; do not add a second storage approval question. Keep raw name, phone, DOB, and other derivation inputs transient and out of chat output, arguments, environment, files, logs, private source-inventory notes, and general memory.

Reuse confirmed opaque credential scopes; distinct confirmed accounts may share one scope when covered by the same protected statement. Use the current private-file credential store and the account's exact saved scope; there is no credential-copy or backend-conversion path. Record honest readiness: `verified` after successful reuse, `not_required` for an observed unprotected PDF or inline statement, otherwise `unverified`. A user may explicitly choose alerts-only coverage while a statement remains unresolved. Remove temporary PDFs, extracted text, and input files in `finally`.

## 4. List source emails and instructions, then hand off to automation

Prepare a concise source inventory before running the report. For each relevant email/statement or group with identical instructions, list:

- Verified mailbox, sender/institution, subject/date, and message ID or supported message link; include each attachment ID and statement period where applicable.
- Confirmed masked financial account, source type, and evidenced payment/transfer system when relevant.
- Documented unlocking recipe and its source, required input names, verification status, and any unresolved detail. Never include identity values or a password.
- Next action or durable disposition: ready for automation, proven duplicate-linked, or visible review with the precise access/extraction/identity gap.

Keep the private handoff metadata and nonsecret instruction provenance outside installed skills and Git, using the setup contract's settings and private source-inventory fields. Do not retain raw email bodies or extraction dumps as the inventory. Unknown credentials or unsupported sources must remain visible; accessible accounts can proceed.

Supply source currency and fractional precision explicitly for every transaction/statement. Keep payment-method labels as optional source metadata. Do not assume an account number length, currency, country, payment system, category taxonomy, or timezone.

Save confirmed account inventory, credential readiness, confirmed timezone when known, and report path with `<moneylens> accounts --data-dir <directory> --input <private-settings.json>`; the agent saves collection/source-inventory notes separately and leaves scheduling choices for step 5. Reuse existing choices; ask only for missing data/access details. Keep one private ledger and report across selected mailboxes. Run from the current project directory where the user invoked the skill. Default a new installation's data directory to that resolved absolute project directory, with `report.html` alongside `ledger.sqlite3`; do not require a Documents folder or change into the installed skill directory. Reuse only a current-format data directory/report path. For a pre-release or unsupported database, request a clean private data directory; do not convert, delete, or overwrite the old files. Pass the resolved `--data-dir` explicitly to helpers and retain it in the scheduling handoff so later working directories cannot redirect the installation.

Invoke the sibling **`$automation`** to prepare the report and perform the initial backfill from the first day of the previous calendar month through today across selected mailboxes. The agent retrieves sources directly through MCP for the selected mailboxes; the current setup selection answers the same pull's selection question. Pass local transaction data to the accounting script and local PDFs to the separate extraction script. Supply source IDs, account mappings, instruction/credential readiness, review gaps, and existing private configuration. Use the sibling's accounting import, reconciliation, and report operations instead of duplicating its workflow in setup. Unsupported provider operations or message layouts must remain explicit gaps; never imply a provider-specific parser works elsewhere.

Require the [ledger contract](../automation/references/ledger-contract.md) for every retrieved statement: cover every page, account/currency section, and transaction occurrence before classification. Every occurrence needs one durable retained, proven duplicate-linked, or visible review outcome. Import eligibility is assessed per account/currency section; unrelated summary sections with missing movement details remain visible document gaps without blocking a reconciled section. Do not fabricate withdrawals or interest dates to complete a deposit summary. Include all bank movements, repayments, credits, fees, and both own-transfer legs. Matching amounts alone do not prove duplicates or ownership; preserve confirmed own transfers outside spending. Statements take precedence over notifications for their account/currency periods; alerts do not fill statement gaps. The agent interprets issuer descriptors from source evidence and supplies any display notes in metadata; processing scripts do not recognize institutional layouts.

After automation writes the report, run `<moneylens> list --data-dir <directory>` and inspect Other by count and spending per currency. Check each merchant with `merchants --merchant <name>`; reuse a cached category, or have the agent decide it from source context and user preferences. Save a resolved reusable decision with `merchants --merchant <name> --category <category>` and correct the row with `update --id <transaction-ID> --category <category>`. Keep genuinely ambiguous merchants uncached. Preserve explicit categories, annotations, original evidence, and the existing report UI. Refresh after corrections and retain resolved decisions in the merchant cache. Keep Spending, Incoming money, Cashflow, Transfers, All transactions, and Review distinct; no Notes column. Backfill completion requires paginated searches, durable source dispositions, and a successful report write. It does not prove statement completeness: missing evidence must say **Completeness not verified** with precise gaps.

## 5. Offer recurring updates after the first report is ready

Before asking any scheduling question or showing a proposal, verify that selected data has been connected and processed: statement PDFs have actually been opened, decrypted where needed, and read; protected credentials have passed unattended reuse; the initial selected-source collection, ledger import, and reconciliation are finished; and the first report has been written and its link presented. An unresolved unlock, retrieval, or extraction task keeps scheduling pending. Proceed with reduced coverage only when the user explicitly chose to exclude/defer that source or use alerts-only coverage; show the accepted gaps in the report. Do not silently treat inaccessible data as connected.

Only now use the user-input tool for any missing refresh frequency, time, or timezone, requesting one choice/value per question and waiting before the next. If several fields are missing, collect frequency, then time, then timezone in separate calls; skip values already known. For a chosen daily frequency, a time-only question may suggest 09:00 in the user's confirmed timezone. Reuse timing and authorization already supplied rather than asking again. If the user supplied timing earlier, remember it but defer the proposal and schedule creation until this readiness check passes. For schedule-only repair, verify existing report/source readiness rather than repeating a completed backfill.

Use the setup contract's scheduling handoff to run **the same `$automation` skill** on the agreed cadence with the existing private data directory. Setup creates/repairs the schedule; automation performs each refresh. Reuse a verified existing job and saved recurring authorization, inspect unknown outcomes before retrying, and preserve paused jobs unless the user requests resuming. Default to one thread heartbeat unless standalone work was requested. Keep its prompt short, referencing the installed skill and private data directory; keep financial details and credentials out of it. Stay quiet while unchanged or non-actionable; notify on meaningful changes, completion, failure, or required user action.

If scheduling is unavailable, deliver the report, retain recurring-access authorization, report the cadence as inactive/unverified, and retry scheduling alone when possible. A setup request authorizes this described recurring handoff after mailbox/inventory/time choices; do not request the same approval again after a tool failure.

Return the source/instruction inventory, verified mailboxes, confirmed masked accounts, credential readiness without secrets, report link, cadence/timezone, and separate **report ready** / **automation active** states. A saved schedule ID does not prove a working job, and an active job does not prove a successful refresh.

Omit statement-covered alert counts and routine explanations that those alerts were not counted again. Statement precedence is automatic bookkeeping; keep its audit history internal unless the user requests it. Show effective confirmed/provisional amounts and actionable data gaps instead.
