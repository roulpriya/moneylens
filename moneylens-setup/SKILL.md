# MoneyLens setup

Prepare the account and credentials for `$moneylens-automation`. Both MoneyLens skills must be installed from this package. Shared helpers and the committed HTML template live in the sibling `moneylens-automation` directory; resolve its actual path before running helpers. Read [setup contract](../moneylens-automation/references/setup-contract.md) for the nonsecret configuration and scheduling handoff.

## Interactive setup

1. **Check Gmail.** Call the connected Gmail profile tool and confirm the actual mailbox. Availability of tools alone is not a connection check. If disconnected, use the supported connection flow and recheck; never collect Google passwords or create an OAuth implementation. Reuse this mailbox's existing MoneyLens data directory. Keep other mailboxes in separate directories.
2. **Discover cards.** Search both statement emails/PDFs and transaction-alert emails over the last three calendar months in the user's timezone. Paginate and inspect actual messages. Infer issuers and masked card identities without requiring a bank list. Match existing ledger cards and reuse their account keys before assigning new ones. Show the number of unique cards found, issuer + last four digits for each, and any unresolved candidates or search gaps. State that this is the count detected in this Gmail period, not proof of all cards owned.
3. **Get the user's card confirmation.** Ask whether the displayed count and list are correct; resolve additions, aliases, and missing/ambiguous cards before finalizing. Ask one question at a time. Confirmation must come from the user, not from an email or inferred silence. Do not call setup complete after an incomplete search or unresolved count.
4. **Verify every required PDF password.** For each confirmed card, determine whether its statement PDFs require passwords. Check the scoped Keychain entry using the native helper's metadata-only status command. Verify by successfully unlocking a recent actual statement. Entry existence alone does not prove validity. For missing/incorrect passwords, use the helper's local masked prompt; after a successful unlock it saves into the user's macOS Keychain. Never ask for passwords in chat, place them in CLI/env/config/Git, or expose a retrieved password to the model. Unprotected statement PDFs are `not_required`; a protected PDF without a usable sample/password remains `unverified` and setup is incomplete. Credential scopes are per mailbox/issuer/card, with document-scoped credentials migrated only after card identity is verified. Read [Gmail and extraction](../moneylens-automation/references/gmail-and-extraction.md).
5. **Save configuration.** Confirm the daily run time in the user's timezone (recommend 09:00 local if unspecified) and the stable local report location. Configure the confirmed inventory using `runtime_state.py configure`. Automatic saving of validated transactions is the product policy; ambiguous items remain for review. Keep credentials exclusively in Keychain. The SQLite ledger retains records and source references, not PDFs or raw extracted text. Remove temporary working copies in `finally`.
6. **Handoff and schedule.** Once Gmail, card confirmation, and every required password are verified, read and execute the sibling `$moneylens-automation` skill for the initial three-month backfill and report. Then create or update a single daily Codex automation at the confirmed local time using the scheduling tool, with a prompt invoking `$moneylens-automation` and the exact data directory. Use the default thread heartbeat unless the user asks for standalone jobs. Reuse the saved automation ID, or inspect existing matching schedules before creating one. Save the returned ID via `runtime_state.py set-automation`. Scheduling failure means setup is not fully complete; report it accurately. Do not write raw automation config/cron files or create a second schedule on rerun.

## Completion

Return the confirmed Gmail account, card count/list, password readiness without secrets, daily local schedule, and the report link. A user's instruction to run this setup includes the daily scheduling handoff above; additional permission is unnecessary once the required inventory and time answers are supplied. Do not schedule during mere skill authoring or a design discussion.

For repair, retain the ledger and report, replace only the invalid credential through the masked prompt, reconfirm changed inventory, and update the existing schedule. Daily runs encountering a new card or password problem route the user here and continue with other known cards; they never open password prompts unattended.
